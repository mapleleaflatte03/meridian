Loom positioning Governance and proof as runtime choice.

Loom is not trying to be the broadest agent shell. It is built for decisions where receipts, authority, budget, and sanctions materially matter.

This compare page is research-facing and evidence-bound. Kernel stays runtime-neutral, while Loom is evaluated as the local runtime surface on install clarity, receipts, and governed execution behavior.

Reality split: breadth assistant vs governed runtime

Claw-family stacks currently lead on breadth, channels, and community gravity. Loom is optimized for governed execution where warrants, authority, treasury controls, and proof-chain behavior drive selection.

Pick by operational requirement, not marketing breadth

Need inspectable governed execution

Pick Loom when the runtime decision changes because you need receipts, authority, budget gates, sanctions, and an honest local boundary.

Need broad assistant UX

Pick OpenClaw or OpenHands when the core requirement is feature breadth, coding environment presence, or assistant surface area.

Need dense orchestration packaging

Pick OpenFang, CrewAI, or LangGraph when orchestration infrastructure is the center of gravity.

Need local memory-heavy agency

Pick IronClaw, TEMM1E, or Goose when persistent local operator ergonomics matter more than institutional governance.

Loom still has to earn three things

01Packaging polish. Install is faster now, but the field still beats Loom on instant first-run polish.
02Memory ergonomics. Loom now has governed memory receipts and personal-agent state, but still trails the strongest local agency systems on density and ergonomics.
03Mindshare. Positioning is clearer than current public attention, which means distribution still lags runtime work.
Loom should borrow execution quality without changing category focus. The priority is better packaging, stronger memory ergonomics, and tighter local-agent UX without diluting governance boundaries.
